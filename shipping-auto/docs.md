# 发货台批量创建发货单 · 使用说明

针对跨境卖货发货台（`seller.kuajingmaihuo.com/main/order-manager/shipping-desk`）的自动化脚本。
把「逐行改实际发货数 → 创建发货单 → 选发货仓库 → 二次确认」这一整套重复操作跑成循环，一轮处理一个仓库，直到列表清空。

---

## 一、它到底做什么

列表里通常混着多个仓库的备货单，而接口的规则是：**一旦你改了某个仓库的实际发货数，其他仓库的行会立刻整行置灰、不可操作**。
所以「全部改完再一次性创建」是不成立的。脚本按下面这个循环走：

| 步骤 | 动作 | 关键点 |
|---|---|---|
| 1 | 打开发货台，等列表加载完 | 识别「暂无数据」，有数据才继续 |
| 2 | 逐行点「修改」→ 填实际发货数 → 点气泡里的「确认」 | 只动**还能点**的行；置灰的属于别的仓库，跳过 |
| 3 | 本页可点的行全改完 → 点「创建发货单」 | 跨页时弹的确认框里点蓝色按钮，把其他同仓库单一并带上 |
| 4 | 创建页把每个「发货仓库」下拉选第一项 | 只动值为空的「请选择」，不碰已填好的「发货店铺」 |
| 5 | 点「确认创建」→ 气泡里点「继续合并，已确认合并发货」 | 白色那个是「取消创建」，不能点 |
| 6 | 页面重定向回发货台 → 回到步骤 1 | 下一轮处理下一个仓库，直到列表 0 条 |

---

## 二、环境准备

```bash
node -v      # 需要 Node 18+（实测 v22 可用）
npm i        # 只装 playwright-core，不下载浏览器
```

- 用的是**本机已安装的 Chrome**（`channel: 'chrome'`），不需要 `npx playwright install`。
- 首次运行会在脚本目录生成 `.pw-profile/`（独立 Chrome 配置目录），**在弹出来的窗口里手动登录一次**，登录态就存在这里，以后不用再登。
- `.pw-profile/` 不要删，删了要重新登录；也不要在脚本运行时手动动里面的文件。

## 三、命令

所有命令在脚本目录下执行：

```bash
cd C:\Users\Administrator\Desktop\test\shipping-auto
```

### npm 脚本

| 命令 | 作用 |
|---|---|
| `npm run probe` | **探测模式**，只读。打印页面上所有按钮文案、输入框 placeholder、「修改」按钮数量，并把完整 HTML 存到 `shots/probe.html`。不改任何数据 |
| `npm run dry` | **演练模式**（= `--dry --debug`）。会**真的点开「修改」气泡**、读上限、然后把气泡关掉，但不填数、不提交。用来验证触发链路和仓库分组 |
| `npm run auto` | **正式执行**。真实修改数据并创建发货单 |
| `npm run verify` | 用 `shots/probe.html` 离线复验选择器能不能抓到行/单号/仓库/按钮状态（不用登录） |
| `npm test` | 跑弹窗按钮单测：验证「取消」和「确认」不会点错 |

### 直接传参（cmd / PowerShell / Git Bash 写法一致）

```bash
node index.js --dry --debug
node index.js --fill=53
node index.js --max-rounds=3
node index.js --cdp=http://127.0.0.1:9222
```

### 参数一览

| 参数 | 默认 | 说明 |
|---|---|---|
| `--fill=N` | `99999` | 要填的实际发货数。**超过该行上限会自动回退成上限值**，所以填 99999 的实际效果通常是「填满」 |
| `--max-rounds=N` | `200` | 最多跑几轮（一轮 = 一个仓库组创建一张单），防死循环 |
| `--slowmo=N` | `120` | 每步操作之间的额外延迟（毫秒）。页面卡、网络慢就调到 300 |
| `--cdp=URL` | 空 | 连接已开远程调试端口的 Chrome，复用你当前窗口的登录态，不另开新窗口 |
| `--dry` | 关 | 演练模式 |
| `--debug` | 关 | 详细日志（输入框实际值、下拉选项、可见性判断等） |
| `probe` / `--probe` | — | 探测模式 |

> 也支持环境变量（`FILL` / `MAX_ROUNDS` / `SLOWMO` / `CDP` / `DRY` / `DEBUG`）。
> 注意不同终端写法不同：cmd 用 `set X=1 && npm run auto`，PowerShell 用 `$env:X="1"; npm run auto`，Git Bash 用 `X=1 npm run auto`。**拿不准就用 `--参数`，哪都能跑。**

## 四、真实的页面结构（脚本就是按这个写的）

这些都是从 `probe.html` 快照和实测气泡 DOM 里扒出来的，不是猜的：

| 元素 | 真实形态 |
|---|---|
| 表格 | 真 `<tr>` / `<td>`（beast-core 组件库），不是 div 拼的 |
| 表头 | 基本信息 \| 收货仓库 \| SKU信息 \| 待发货数 \| 实际发货数 \| 剩余需发货数 \| 创建时间 \| 操作 |
| 「修改」 | `<a data-testid="beast-core-button-link"><span>修改</span></a>` |
| 置灰态 | class 追加 `BTN_disabled_5-111-0`，`pointer-events: none` |
| 「创建发货单」 | 真 `<button>`，禁用时同样是 `BTN_disabled_5-111-0` |
| 仓库列 | 第 3 个 `td`，文本以「仓」结尾，**存在 rowspan 合并**（部分行没有自己的仓库名，需向上继承） |
| 修改气泡 | 从 input 往上**第 11 层**才是含「确认/取消」的气泡根 —— 少走一层就找不到确认按钮 |
| 仓库下拉 | 触发框是值为空的 `input[placeholder="请选择"]`，面板 portal 到 body、绝对定位在触发框正下方 |

注意几个**实测遇到的文案版本差异**，脚本都做了兼容：

| 场景 | 文案 |
|---|---|
| 数量上限提示 | 「最大不超过20」/「不能超过该数 35」两种都见过 |
| 批量确认框 A | 「本次共计发货 95 件，确认创建发货单？」→ 蓝色「发货数一致，继续创建」 |
| 批量确认框 B | 「本次计划发货 37 件，确认批量发货吗？」→ 蓝色「取消其他，去创建发货单」 |
| 二次确认气泡 | 「…打印发货单，确认创建？」→ 蓝色「继续合并，已确认合并发货」/「继续创建，已确认一致」 |

## 五、几个关键实现细节

### 1. 行去重不能按单号

同一备货单拆多个 SKU 会出多行，单号相同。**去重键是「单号 + SKU ID」**，用单号会把后面的行误判成「已改过」而漏改。

### 2. 「能不能点」比「改没改」更重要

判定顺序：`disabled` / `aria-disabled` / `pointer-events:none` / `cursor:not-allowed` / class 含 `disabled|gray|forbid` / `opacity<0.5`。
外加运行时兜底：**点完 4 秒内没弹出输入框，一律当作不可操作**，按 Esc 清场跳过。不依赖页面用什么方式置灰。

### 3. 修改成功的判定

三重，依次降级：

1. 气泡里的「确认」被点到且气泡关闭（`clickConfirmNearInput`）
2. 被上限拦下 → 读上限值重填一次
3. 还不确定 → 直接看这行还带不带「未修改实际发货数」标记（页面自己的状态最可信）

判定为失败就停，不会带着错状态往下走。

### 4. 气泡/弹窗按钮定位统一走 `locateFloatingButton()`

同时认模态框和气泡：class 命中 `modal|dialog|popup|popover|popconfirm|bubble|overlay`，或 `position:fixed/absolute` + `z-index≥50`。
命中提示文案 → 向上找容器 → **在容器内部优先挑蓝色主按钮**（`BTN_primary`），再退到文案匹配，兜底要求文案长度 ≤ 24 字，避免把整个弹窗容器当按钮点。
定位不到就返回 null 什么也不点 —— **宁可漏，不乱按**。

### 5. 仓库下拉用纯几何定位

不靠 class 名（beast-core 一版一个类名），流程是：

1. 只挑**值为空**的 `input[placeholder*="请选择"]`（已填好的「发货店铺」不碰）
2. 键盘 `↓` + `Enter`
3. 读回值还是空 → 几何兜底：取「触发框正下方、横向重叠、最近的文字叶节点」
4. 失败会关掉重开重试一次

### 6. 提交前的硬保险

点「确认创建」之前统计页面上还剩几个空「请选择」。**只要 > 0 就直接中止 + 截图 `warehouse-missing.png`，绝不提交**。
这条是为了避免「仓库空着却创建成功」——之前踩过这个坑。

## 七、排错对照表

这些是实际踩过的坑，症状对得上就直接看结论。

| 症状 | 原因 | 处理 |
|---|---|---|
| 日志刷「修改成功」但屏幕不动 | 旧版 dry 模式直接 return，不点任何按钮 | 已修，现在 dry 会真点开气泡。`npm run auto` 是真实操作 |
| 填了值但没提交 | 确认按钮向上查找层数不够（气泡根在第 11 层） | 已修，向上查 14 层 |
| 只改了第一行就停 | 确认后误判为失败（气泡关了还在找新冒出的 input） | 已修，改用「气泡输入框消失 + 未修改标记消失」双判定 |
| 同仓库后几行没改 | 去重键用了单号，多 SKU 行被当成已改 | 已修，改 `单号+SKU` |
| 卡在批量确认弹窗 | 匹配的文案是「本次计划发货」，实际是「本次共计发货」 | 已修，两种文案都兼容，且优先点蓝色主按钮 |
| 仓库全空却创建成功 | 点到了「发货店铺」下拉的选项（Magic Sticker当前） | 已修：只动值为空的请选择 + 提交前空值保险 |
| 仓库选不中 | `boundingBox()` 返回 `{width,height}`，代码按 `{w,h}` 解构 → 全是 NaN | 已修，参数名对齐 |
| 第二行点不动/超时 | 上一行气泡没关掉，挡住下面元素 | 已修：dry 用「取消」关气泡；正式流程点确认后气泡自然关闭；点击失败会 Esc 后 force 重试 |
| 列表明明有数据却判「暂无数据」 | 页面还没加载完 | `settle()` 会等 loading 和网络空闲，`--slowmo` 可再加大 |
| 启动报 profile 被占用 | 上次脚本开的 Chrome 窗口没关 | 关掉那个窗口再跑；脚本和你自己的 Chrome 是两个独立实例，不冲突 |

## 八、已知限制

1. **「加入其他同仓库单」跨页弹窗未实测**。逻辑上走的是批量确认框的蓝色按钮（`取消其他/加入其他/去创建发货单` 都匹配），但列表清空后还没遇到第二页同仓库单的场景。第一次遇到时留意日志 `⇢ 出现批量发货确认框…`，把那一行发出来就能钉死。
2. **依赖本机 Chrome**。机器上没装 Chrome 会启动失败（用的是 `channel:'chrome'`，不是内置 Chromium）。
3. **不能两个实例同时跑**。`.pw-profile` 是独占的，会抢锁。
4. **页面改版后会失效**。脚本靠文案 + 结构定位，官方改表头/改按钮文案都可能打穿。届时先 `npm run probe`，把 `shots/probe.html` 发出来重新对一遍选择器。

## 九、建议的首次使用顺序

```bash
npm i                  # 装依赖
npm run probe          # ① 只读探测，顺手在里面登录
npm run verify         # ② 离线复验选择器（可选，但能提前发现结构变化）
npm run dry            # ③ 演练：看分组对不对、气泡能不能弹
npm run auto           # ④ 正式跑
```

第 ③ 步重点看两件事：**同一仓库的行是不是连续被处理**、**点「创建发货单」前那行「另有 N 行仍被锁定」的数字对不对**。这两个对了，正式跑就稳。
